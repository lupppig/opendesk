opendesk reads its configuration from environment variables. The self-host bundle keeps them in `/opt/opendesk/.env`; for local development, copy `.env.example` in the repository to `.env`.

Empty values use the default. Booleans accept `true`/`false`, `1`/`0`.

<Callout title="Changing a setting">

Edit `/opt/opendesk/.env`, then run `/opt/opendesk/opendesk-ctl start` (it runs `docker compose up -d`): the containers whose settings changed are recreated with the new values. A plain restart keeps the old ones. Settings for the bundle itself, such as the domain and the compose profiles, are in [Docker Compose](/self-hosting/docker-compose/#the-env-file).

</Callout>

## Refuses to boot

opendesk checks its secrets at start and refuses to run when they are unsafe:

- `AUTH_SECRET` shorter than 32 bytes, or empty. Only a development instance whose `APP_URL` and `API_URL` are both on `localhost` falls back to a public development secret.
- `CREDENTIALS_KEY` missing or not 32 bytes, with the same localhost-only development fallback, or a key in `CREDENTIALS_KEY_PREVIOUS` that is not 32 bytes.
- In production, `COOKIE_SECURE=false` while `API_URL` is `https`.
- In production, embedded NATS listening beyond `127.0.0.1` without `NATS_TOKEN`.
- `OPENDESK_ROLE` other than `all`, `api` or `worker`.
- `STRIPE_SECRET_KEY` set without `STRIPE_WEBHOOK_SECRET` and `STRIPE_PRICE_PRO`.
- Only some of `APNS_KEY`, `APNS_KEY_ID` and `APNS_TEAM_ID` set, `PUSH_RELAY_SERVE=true` without an APNs key, or a `PUSH_RELAY_URL` that is not an `https` origin.
- `HELP_DOMAIN` that is not a domain name, `HELP_PROXY_SECRET` shorter than 32 bytes, only one of `CLOUDFLARE_SAAS_ZONE_ID` and `CLOUDFLARE_SAAS_TOKEN`, or Cloudflare for SaaS with neither `HELP_CNAME_TARGET` nor `HELP_DOMAIN`.

The realtime gateway also refuses to start with an `AUTH_SECRET` under 32 bytes.

## Help centers

Where each brand's help center lives, and how custom domains reach it. See [Help center addresses](/guides/help-center-addresses/) for what customers do, and [Docker Compose](/self-hosting/docker-compose/#help-center-addresses) for the DNS and certificates of a self-hosted instance.

| Variable | Default | Meaning |
| --- | --- | --- |
| `HELP_DOMAIN` | empty | Puts each help center at `<slug>.HELP_DOMAIN`, such as `https://acme.help.example.com`, with the scheme of `APP_URL`. Needs a wildcard DNS record for `*.HELP_DOMAIN`. Empty keeps help centers at `APP_URL/help/<slug>`. opendesk Cloud uses `opendeskhelp.com`. |
| `HELP_CNAME_TARGET` | `custom.HELP_DOMAIN` with Cloudflare for SaaS, else the host of `APP_URL` | The hostname customers point their custom domain's CNAME at. It must reach this instance. |
| `HELP_PROXY_SECRET` | empty | At least 32 bytes, shared with an edge proxy in front of the help centers (opendesk Cloud's help worker). When set, the help center host is read only from a request that carries the secret (`OD-Help-Secret`), with `OD-Help-Host` and `OD-Help-Client-IP`. Leave it empty when Caddy or another proxy forwards the `Host` header as is. |
| `CLOUDFLARE_SAAS_ZONE_ID` | empty | A Cloudflare zone with Cloudflare for SaaS: verified custom domains become custom hostnames of it, with certificates from Cloudflare. Set together with the token. |
| `CLOUDFLARE_SAAS_TOKEN` | empty | A Cloudflare API token with **SSL and Certificates: Edit** on that zone only. Without the pair, the instance's own proxy issues certificates on demand (Caddy, asking `GET /v1/public/help-domains/tls?domain=`). |

## Secrets

| Variable | Default | Meaning |
| --- | --- | --- |
| `AUTH_SECRET` | none (development on localhost: a public development secret) | At least 32 bytes. Signs every JWT. **Must be identical** in opendesk and the realtime gateway. |
| `CREDENTIALS_KEY` | none (development on localhost: a public development key) | 32 bytes, hex or base64. Encrypts mailbox credentials, OAuth tokens, webhook secrets and TOTP secrets with AES-256-GCM. **Change it only with the old key in `CREDENTIALS_KEY_PREVIOUS`**, as in [Replace CREDENTIALS_KEY](/self-hosting/hardening/#replace-credentials_key): on its own, a new key leaves existing credentials unreadable. |
| `CREDENTIALS_KEY_PREVIOUS` | empty | Keys `CREDENTIALS_KEY` replaced, separated by commas, in the same format. Values they encrypted still decrypt, and a background pass encrypts them again with `CREDENTIALS_KEY`; remove this once the logs say it can be removed. |

<Callout type="warning" title="Back up CREDENTIALS_KEY">

Generate each with `openssl rand -hex 32`. `.env` holds the only copy of `CREDENTIALS_KEY`: back it up with the database, since a backup without it cannot decrypt stored credentials. After replacing the key, keep the old one for as long as you keep backups taken with it.

</Callout>

### Mailbox sign-in

Connecting a mailbox with Google or Microsoft sign-in has its own switch per provider. It is on when that provider's client is configured, and it does not change how people sign in to opendesk. The sign-in sends replies from the mailbox; with [receiving over IMAP](#receiving-over-imap) on, it can also sync the mailbox.

| Variable | Default | Meaning |
| --- | --- | --- |
| `GOOGLE_MAILBOX_OAUTH` | `true` when `GOOGLE_CLIENT_ID` is set | `false` stops offering Google sign-in for new mailboxes. Mailboxes already connected with it keep working and can reconnect. |
| `MICROSOFT_MAILBOX_OAUTH` | `true` when `MICROSOFT_CLIENT_ID` is set | The same for Microsoft. |
| `MAILHOST_ISPDB` | `false` (`true` with billing configured) | When detecting a mailbox's servers, also look up unknown domains in Thunderbird's public ISPDB (`autoconfig.thunderbird.net`). The domain's own autoconfig, MX and SRV records are always used. |

With a provider's mailbox sign-in off, or its client not configured, the mailbox wizard offers the other ways: any provider forwards its mail into opendesk, and replies go out through the mailbox's SMTP server (for Gmail and Google Workspace with an app password, for Microsoft 365 when the tenant allows SMTP AUTH) or a sending service, or, with `MAILBOX_SYSTEM_SEND` on, through opendesk. With receiving over IMAP on, other providers, and Gmail and Google Workspace with an app password, can also connect over IMAP and SMTP with the settings the wizard detects.

A value that is not `true` or `false` (or `1` and `0`) turns the switch off. The API answers a new connection with `403 mailbox_oauth_disabled`, and the web app reads the same list from its runtime config (`mailboxOAuth`).

### Receiving over IMAP

Every mailbox can receive by forwarding. A self-hosted instance can also let mailboxes receive over IMAP: generic IMAP mailboxes, and Google and Microsoft mailboxes connected to sync. opendesk Cloud runs with it off, so its mailboxes receive by forwarding and Google and Microsoft connect send-only.

| Variable | Default | Meaning |
| --- | --- | --- |
| `MAILBOX_IMAP` | `true` | `false` turns receiving over IMAP off. The wizard then offers forwarding to receive, and Google and Microsoft sign-in to send only; SMTP sending stays available. Mailboxes that read over IMAP are kept with their tickets, but no longer polled: their page shows that receiving is off until they switch to forwarding. |

With it off, the API refuses an IMAP, Google or Microsoft `inbound_kind` and a Google or Microsoft connection that syncs, with `422 imap_off`, and the web app reads the same setting from its runtime config (`mailboxImap`). Workspaces with [Collab](#collab-your-own-mail-accounts) are the exception for generic IMAP while `COLLAB_IMAP` is on: their mailboxes may still receive over IMAP and SMTP, through the same network guard. They can also connect Google and Microsoft to read the inbox directly through the Gmail API or Microsoft Graph, with the Collab clients below, so no forwarding is needed; that works whatever `MAILBOX_IMAP` says. Syncing Gmail needs the restricted `https://mail.google.com/` scope, and Microsoft the `IMAP.AccessAsUser.All` permission, on your OAuth apps; see [Google and Microsoft OAuth](/self-hosting/oauth-apps/).

### Sending through opendesk

Every mailbox can send through Google or Microsoft, or over SMTP through its mail server or a sending service such as Resend or Postmark. A self-hosted instance can also let mailboxes send **through opendesk**: replies go out through the [platform email](#platform-email) (`MAIL_DRIVER`), from `MAIL_FROM` with the mailbox's name, and customers' answers come back to the mailbox's address. opendesk Cloud runs with it off, so every mailbox sends from its own address.

| Variable | Default | Meaning |
| --- | --- | --- |
| `MAILBOX_SYSTEM_SEND` | `true` | `false` turns sending through opendesk off. The wizard and the mailbox's settings then offer Google, Microsoft and SMTP only. Mailboxes that send through opendesk are kept with their tickets and settings, but send nothing: the Mailboxes page marks them **Not sending**, the reply box in their tickets says the address can't send yet, and their page asks for SMTP or a Google or Microsoft connection. Automations skip their email replies, Ollie's email answers wait as suggested replies, and auto-replies and satisfaction surveys are not sent. |

With it off, the API refuses `outbound_kind` `system` on a new or changed mailbox with `422 system_send_off`, and an email reply from a mailbox that still has it with `422 mailbox_cannot_send`; a reply queued before the change fails with that reason. Mailboxes report `sending: "system_off"`, and the web app reads the setting from `GET /v1/mailboxes/connect-options` (`system_send`). See [Mailboxes](/api/resources/mailboxes/#sending-through-opendesk).

## Collab: your own mail accounts

Collab lets each member connect their own email account (Google, Microsoft or any IMAP server) and read and handle it in opendesk like a mail client: every folder and label, read and unread, stars, archive, move, trash and spam, replies and new mail, with each change made at the provider too. An account is private to whoever connected it, or shared with the workspace or with teams and people, and any single conversation can be shared, assigned and discussed on its own. A self-hosted instance has it for every workspace.

| Variable | Default | Meaning |
| --- | --- | --- |
| `COLLAB` | `true` | `false` turns Collab off on this instance. Accounts already connected are kept but not synced, and the Mail pages are gone. |
| `COLLAB_IMAP` | `true` | Offer accounts on any IMAP and SMTP server (with an app password where the host needs one). |
| `COLLAB_GOOGLE_CLIENT_ID`, `COLLAB_GOOGLE_CLIENT_SECRET` | the mailbox client (`GOOGLE_MAILBOX_CLIENT_ID`) | The Google client Gmail and Google Workspace accounts connect with. It needs the Gmail API enabled and the `openid`, `email`, `profile`, `https://www.googleapis.com/auth/gmail.modify` and `https://www.googleapis.com/auth/gmail.settings.basic` scopes on its consent screen (the second keeps each account's signature, From name and vacation responder in sync with Gmail). |
| `COLLAB_MICROSOFT_CLIENT_ID`, `COLLAB_MICROSOFT_CLIENT_SECRET` | the mailbox app (`MICROSOFT_MAILBOX_CLIENT_ID`) | The Microsoft app Microsoft 365 and Outlook.com accounts connect with, with the Microsoft Graph delegated permissions `Mail.ReadWrite`, `Mail.Send`, `User.Read`, `MailboxSettings.ReadWrite` (automatic replies and categories) and `offline_access`. |

Add these redirect URIs to the clients: `<API_URL>/v1/collab/accounts/oauth/google/callback` and `<API_URL>/v1/collab/accounts/oauth/microsoft/callback`. Support mailboxes connected to read the inbox directly sign in with these clients too, through the mailbox redirect URIs: when the Collab clients are separate from the mailbox clients, also add `<API_URL>/v1/mailboxes/oauth/google/callback` and `<API_URL>/v1/mailboxes/oauth/microsoft/callback` to them. `gmail.modify` is a restricted Google scope and `gmail.settings.basic` a sensitive one: an app used by people outside your own Google Workspace organization needs Google's verification for them. An account connected before you added the settings scope or permission keeps syncing its mail, with its settings read only (Gmail) or not synced (Outlook automatic replies) until it is reconnected.

## Bot protection and analytics

| Variable | Default | Meaning |
| --- | --- | --- |
| `TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET` | | Cloudflare Turnstile on login, registration and password reset. |
| `POSTHOG_KEY` | | Product analytics. Empty sends nothing. |
| `POSTHOG_HOST` | `https://us.i.posthog.com` | PostHog host. |

Server-side analytics is off while `POSTHOG_KEY` is empty. Setting it opts the instance into
the backend event schemas: only known event names and approved scalar properties are sent;
unknown events, nested values, and unapproved properties are discarded. User and workspace
UUIDs identify events. Message text, email addresses, credentials, and exception messages are
not included. Browser analytics has separate `WEB_POSTHOG_KEY` and `WEB_POSTHOG_HOST` settings
and is not limited by these schemas.
The receiving PostHog project controls access, data residency, and retention, so configure
those settings for your deployment; the instance does not set PostHog retention.

| `TYPESAFE_MODEL` | `jev-latest` | Jev model or alias. Pin a version such as `jev-1.13.0` to keep answers stable across releases. |

Semantic search needs the Postgres `vector` extension (pgvector). Without it, opendesk uses full-text search.

## Native apps

Settings for the [desktop](/guides/desktop-app/) and [iPhone](/guides/iphone-app/) apps. The desktop app needs none of them. See [Push notifications](/self-hosting/push-notifications/) for choosing a push mode.

| Variable | Default | Meaning |
| --- | --- | --- |
| `PUSH_RELAY_URL` | empty (off) | Send iPhone pushes through this relay when there is no APNs key: an `https` origin, such as `https://api.opendesk.sh`. The relay sees this instance's address, the notification type and the ticket number, never ticket text, names or email addresses. |
| `APNS_KEY` | empty | APNs auth key: the `.p8` file as PEM text or base64. With a key, the instance sends pushes itself (direct mode). |
| `APNS_KEY_ID` | | The key's id. Required with `APNS_KEY`. |
| `APNS_TEAM_ID` | | The Apple developer team that owns the key and signs the app. Required with `APNS_KEY`. |
| `APNS_TOPIC` | `sh.opendesk.app` | The bundle id of the app that receives pushes. |
| `APP_ATTEST_APP_IDS` | empty (off) | Comma-separated app ids (`TEAMID.bundle`) whose App Attest proofs are accepted in place of Turnstile on login, registration and password reset. Needed for the iPhone app only when Turnstile is on. |
| `APP_ATTEST_DEVELOPMENT` | `false` | Also accept App Attest keys from development builds (run from Xcode). Leave off in production. |
| `PUSH_RELAY_SERVE` | `false` | Cloud only: serve the push relay (`/v1/push/relay/*`) for other instances. Needs an APNs key. |

Push mode follows from these: an APNs key means direct, else `PUSH_RELAY_URL` means relay, else off. `GET /v1/auth/config` reports it under `native.push`.

Every instance answers `GET /v1/push/instance-key` with the public half of a key derived from `AUTH_SECRET`, which the relay uses to check that pushes come from this instance. Changing `AUTH_SECRET` changes it.

| Variable | Default | Meaning |

## Realtime gateway

The `realtime` container reads its own variables:

| Variable | Default | Meaning |
| --- | --- | --- |
| `PORT` | `4000` | Listen port. |
| `AUTH_SECRET` | | **The same value** as opendesk. Verifies socket tokens. |
| `NATS_URL` | | NATS to subscribe to: opendesk's embedded server (`NATS_LISTEN`) or your cluster. |
| `NATS_TOKEN` | | NATS token. |
| `CHECK_ORIGINS` | | Comma-separated browser origins allowed to open agent sockets, such as `https://desk.example.com`. The chat widget endpoint (`/socket/widget`) accepts any origin, since it takes only widget tokens. |
| `SECRET_KEY_BASE` | | Phoenix secret. Generate with `openssl rand -hex 48`. |
| `CLUSTER_DNS` | empty | A DNS name that resolves to every gateway node, so Presence spans nodes. A single node needs nothing. |
| `POSTHOG_KEY`, `POSTHOG_HOST` | | Optional connection metrics and errors. |
