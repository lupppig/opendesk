# opendesk desktop

The desktop app for macOS, Windows and Linux: an Electron shell around an
instance's own web app, adding what a browser can't: OS notifications, a dock or
taskbar badge, `opendesk://` links, auto-update and a translucent window
(vibrancy on macOS, mica on Windows 11). The contract is
[`contracts/native.md`](../contracts/native.md), "Desktop shell".

```
src/main/      main process: window, server picker, IPC, OAuth, notifications, menu, updates
src/preload/   instance.ts exposes window.opendeskDesktop; picker.ts serves the server picker
src/picker/    the server picker and the offline page (plain TS, brand tokens, Geist)
scripts/       build.mjs (esbuild), icons.cjs (renders build/ icons from brand/)
build/         icons and macOS entitlements for electron-builder
```

It works with opendesk Cloud and any self-hosted instance; the server is chosen
at runtime and remembered. The web app does the rest when it sees
`window.opendeskDesktop` (`web/src/lib/desktop.ts`): it sets
`<html data-desktop>`, lays itself out for the window chrome, mirrors
notifications, keeps the badge in step and runs OAuth sign-in through the shell.

## Develop

The desktop package has its own lockfile, like `web/`, `site/` and `docs/`, so run
it from `desktop/` (or with `pnpm -C desktop …` from the root).

```sh
cd desktop
pnpm install
pnpm dev                    # builds dist/ and opens the app: the server picker on first launch
```

Point it at a local instance without the picker:

```sh
cd web && pnpm dev:mock     # or `pnpm dev` against a running API
cd desktop && OPENDESK_DESKTOP_URL=http://localhost:5173 pnpm dev
```

Development builds (unpackaged) also accept `http://` for localhost and private
addresses, keep their settings apart (`opendesk-dev` in the app data folder) and
add a few switches after `pnpm dev --`:

| switch | does |
| --- | --- |
| `--url=<address>` | same as `OPENDESK_DESKTOP_URL` |
| `--picker=1` | show the server picker even when a server is saved |
| `--theme=light\|dark` | start the web app in that theme |
| `OPENDESK_DESKTOP_SANDBOX=<dir>` | a throwaway run for automated testing: settings in `<dir>`, no `opendesk://` handler, no OS notifications, badge or Dock icon, an invisible click-through window |
| `--capture=<dir>` | save screenshots after load (`--capture-paths=/a;;/b\|script`, `--capture-name`, `--capture-quit=1`); each is also composited over a stand-in for the macOS material with the traffic lights drawn in, since a page capture has neither |

`pnpm typecheck` checks main, preloads and picker. `pnpm icons` re-renders
`build/icon.png` (macOS grid) and copies the Windows and Linux icons from `brand/icons`.

## Package

```sh
pnpm run package:dir        # an unpacked app in release/ for a quick check
pnpm dist                   # installers for this OS in release/, publishing nothing
```

| OS | artifacts |
| --- | --- |
| macOS | `opendesk-<v>-mac.dmg` and a `.zip` (universal: Apple silicon and Intel), hardened runtime |
| Windows | `opendesk-<v>-setup.exe` (NSIS, per user, x64 and arm64) |
| Linux | `.AppImage` and `.deb` (x64 and arm64) |

App id `sh.opendesk.desktop`, product name `opendesk`, URL scheme `opendesk://`.

## Release

Push a tag `desktop-v<semver>`: `desktop-v0.2.0` for a stable version,
`desktop-v0.2.0-beta.1` (or any other prerelease, such as `-rc.1`) for a beta.
`.github/workflows/desktop.yml` builds on macOS, Windows and Linux, then:

1. creates the GitHub release `desktop-v<version>` with every installer, the
   update metadata (`latest*.yml`, `beta*.yml`, blockmaps) and `SHA256SUMS`. Its
   notes start with the download links and go on with the changes since the
   previous desktop release, generated by GitHub (the previous stable tag for a
   stable version, the previous tag of any kind for a beta). It is never marked
   Latest: the repository's Latest release is the server's `v*` one;
2. refreshes the rolling `desktop-latest` release, which installed apps read
   (`https://github.com/useopendesk/opendesk/releases/download/desktop-latest`,
   electron-updater's generic provider) at launch and every six hours:

   | tag | uploads to `desktop-latest` | removes |
   | --- | --- | --- |
   | stable | its files, `latest*.yml`, `beta*.yml` (unless a newer beta is out), the stable download names and `version.json` | every older file |
   | beta | `beta*.yml` and the installers they point at | what the previous beta files pointed at, unless still in use |

   The stable download names are what [opendesk.sh/download](https://opendesk.sh/download)
   links to: `opendesk-mac.dmg`, `opendesk-windows.exe`,
   `opendesk-linux-x64.AppImage`, `opendesk-linux-arm64.AppImage`,
   `opendesk-linux-amd64.deb` and `opendesk-linux-arm64.deb`, plus `version.json`
   (`{version, date, notes_url}`), which the site reads at build time;
3. after a stable version, runs the Deploy workflow with `target=site`, so the
   download page shows the new version.

Installed apps choose their channel in the app menu (**Get beta updates**). A
stable version is written to both channels, so beta users get any stable
version newer than their beta. Updates never go backwards: someone who leaves
the beta keeps their version until a stable one passes it.

A manual run of the workflow packages all three as workflow artifacts and
publishes nothing. Pull requests touching `desktop/` typecheck and build.

### Signing

Signing and notarization run only when their secrets exist (repository
Settings > Secrets and variables > Actions). Without them the builds are
unsigned: macOS Gatekeeper and Windows SmartScreen warn on first launch, and
macOS won't install updates into an unsigned app.

| secret | for | where to get it |
| --- | --- | --- |
| `CSC_LINK` | macOS signing: the Developer ID Application certificate and its private key, as a base64 .p12 | Apple Developer > Certificates, a "Developer ID Application" certificate exported from Keychain Access (`base64 -i cert.p12`) |
| `CSC_KEY_PASSWORD` | the password of that .p12 | chosen when exporting it |
| `APPLE_API_KEY` | macOS notarization with an App Store Connect API key: the .p8, base64 | App Store Connect > Users and Access > Integrations > App Store Connect API, a Team key with the Developer role (`base64 -i AuthKey_XXXX.p8`) |
| `APPLE_API_KEY_ID` | that key's id | the same page |
| `APPLE_API_ISSUER` | the issuer id | the same page, above the keys |
| `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID` | notarization with an Apple ID instead of an API key (all three) | account.apple.com > App-Specific Passwords; the team id from Apple Developer > Membership |
| `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET` | Windows signing with Azure Trusted Signing: an app registration allowed to sign | Microsoft Entra ID > App registrations (a client secret), given the "Trusted Signing Certificate Profile Signer" role on the signing account |
| `AZURE_TRUSTED_SIGNING_ENDPOINT` | the signing account's region endpoint, e.g. `https://eus.codesigning.azure.net` | Azure portal > the Trusted Signing account > Overview |
| `AZURE_TRUSTED_SIGNING_ACCOUNT` | the signing account name | the same |
| `AZURE_TRUSTED_SIGNING_PROFILE` | the certificate profile name | the account > Certificate profiles |
| `AZURE_TRUSTED_SIGNING_PUBLISHER` | the publisher name exactly as in the certificate (the profile's subject CN); installed apps check updates are signed by it | the certificate profile |
| `WIN_CSC_LINK`, `WIN_CSC_KEY_PASSWORD` | Windows signing with a certificate file instead (base64 .pfx and its password) | a code signing certificate authority |

Notarization uses the API key when all three `APPLE_API_*` are set, otherwise
the Apple ID trio. Windows uses Azure Trusted Signing when its four
`AZURE_TRUSTED_SIGNING_*` are set, otherwise `WIN_CSC_LINK`.

A fork can point its builds at its own feed with `OPENDESK_UPDATE_URL` at package time.

## Security model

The window shows the instance's web app and nothing else, with the browser's
own protections on:

- **Renderer**: `contextIsolation`, `sandbox`, no Node integration, `webSecurity`
  on, no `<webview>`, no `remote`. The preloads only bridge named IPC messages.
- **Navigation**: the window stays on the instance's app and API origins (from its
  `config.json`). Any other link, redirect or `window.open` is refused in the app
  and opened in the default browser, https only (and `mailto:`).
- **IPC**: every message is answered only for the instance window's top frame on
  the instance's app origin, and every argument is checked in main: notification
  text is length capped and its `path` must be a same-origin app path; the badge
  an integer; `openExternal` an https URL; `oauth` exactly
  `{apiOrigin}/v1/auth/oauth/{provider}/start`.
- **Permissions**: notifications and the clipboard, for the instance only. Every
  other permission and device request is denied.
- **Sign-in**: OAuth runs in the default browser (providers refuse embedded
  browsers) with PKCE. Main makes the verifier, adds `client=native` and the
  challenge to the start URL, and waits for `opendesk://auth/callback`; the page
  exchanges the code with the verifier itself so the session cookie lands in the
  app. A code without its verifier is useless, so a forged callback link can't
  sign anyone in. One flow at a time, ten minutes at most.
- **Session**: the same HttpOnly refresh cookie as the web app, in the app's own
  cookie store. The shell never sees a token. Requests carry the user agent
  suffix `opendesk-desktop/<version>`, so sessions show as the desktop app.
- **Links**: `opendesk://open?path=…` opens only app paths of the current instance.
- **Servers**: the address is normalized to an https origin and checked by
  reading `<origin>/config.json` before it is saved (http only to local
  addresses in development builds).
- **Connect flows** (Gmail, Outlook, MCP tools) open the same settings page in
  the default browser; the result reaches the app through realtime events.
- **Updates**: from GitHub Releases over https, verified by electron-updater
  (sha512 from the release metadata, and the code signature on macOS and
  Windows when signed), never to an older version. The page can read the
  update state, ask for a check, a restart into a downloaded update or a
  channel (`stable` or `beta`), nothing more.
